# Superior Point（SP）主题与设计语言框架

> **讨论整合稿 v0.5** · 2026-10-10  
> **文档性质**：产品与架构讨论记录，不是已实现功能说明，也不是立即开发的技术规格。  
> **当前范围**：主题、设计语言、主题资源、主题切换、AI/MCP 协作、主题创作方法。  
> **开发状态**：主题体系暂缓实施；本文用于保存既有讨论与指导后续决策。  
> **决策标记**：`已确定` = 用户明确选择的方向；`推荐` = 当前讨论中较一致但仍可调整的建议；`待定` = 尚未确认或需要验证的方案。

## 0. 执行摘要

Superior Point 是 AI-Native 的网页幻灯片创作平台，计划使用 reveal.js 负责演示，通过结构化文档模型与 MCP 让用户及外部 AI 共同编辑。主题系统不应变成“固定模板集合”或“限制强模型的详细提示词”。

**核心定义**：

> **每个主题代表一门独特的设计语言。** 它具备可辨识的视觉身份、可执行的基础样式、运动语言，以及可选的视觉案例、布局、组件和专属资源。SP 提供通用编辑与动画能力；AI 能参考、组合、改造乃至突破主题资源。

**当前已确定的五项方向**：

1. **新建演示文稿分三个入口**：从主题创建 / 从模板创建 / 从空白创建；AI 不是独立第四入口，而是贯穿三者的创作方式。
2. **布局和组件为 `optional`**：某套主题可以附带，但不要求每套主题拥有固定页面布局或组件库。
3. **动效以 `language` 为核心**：主题表达运动气质、节奏与空间逻辑，具体动画由用户或 AI 根据内容编排；允许存在主题独有的适配动效。
4. **主题切换默认 `skin`**：保留页面内容、结构与布局，不主动重新设计，只变更与主题关联的样式。
5. **视觉参考 `both`，资源复用 `shared`**：支持参考图片与可编辑页面案例并存，允许跨主题使用布局、动效、图形及组件资源。

**重要但尚非硬性规定的方向**：一个主主题 + 可组合外部资源；基础样式 → 主题家族 → 主题变体的浅继承；少量通用 AI Skill + 主题设计上下文；从真实案例中提炼设计语言，再将其固化成主题包。

## 1. 产品概念与边界

### 1.1 主题、模板、空白的区别〔已确定〕

| 创建方式 | 主要提供 | 是否预置具体内容与页面结构 | AI 自由度 |
|---|---|---|---|
| 从主题创建 | 视觉语言、基础样式、可选设计资源 | 不强制，通常为空白或轻量起始页 | 很高 |
| 从模板创建 | 一份已组织好的可编辑演示文稿 | 是，可以包含占位内容、示例页面和主题引用 | 可以改造、删除、重排 |
| 从空白创建 | 基础画布与必要渲染默认值 | 否 | 最大 |

主题负责“**看起来属于哪一种设计语言**”；模板负责“**从什么现成作品开始编辑**”。空白并不是无样式：仍需要 SP 基础字体、背景、坐标和渲染规则。

### 1.2 AI 的位置〔已确定的方向〕

AI 能辅助三种创建方式，但不是第四种创建类别。现阶段优先让 Codex、Claude Code 等兼容客户端通过 **SP MCP** 操作文档；不要求立即开发 SP 内置 AI Agent。

### 1.3 主题不是什么

- 不是一份规定封面、目录、正文、结尾顺序的 PPT 模板。
- 不是由大量预制卡片和固定位置拼出的受限页面生成器。
- 不是每个主题必须具备的一份完整 Skill 或冗长操作手册。
- 不是强制所有动画按固定时长、顺序和转场运行的规则集。
- 不默认等于可运行任意 JavaScript 的插件。

主题可以提供可选的布局、组件和动画资源，但它们应被视为**创作素材与能力**，而不是必需的拼装步骤。

## 2. 一套主题应包含什么

### 2.1 主题身份（Design Identity）〔核心〕

用简明语言定义：这是什么设计语言、希望表达怎样的气质、与其他风格的识别差异在哪里。优先描述视觉层次、空间组织、材料与运动之间的关系，不把某个具体颜色/圆角数值视为全部身份。

示例（仅是探索假设）：Noema 偏向清晰层级、充足留白、灵活空间秩序和连续且有逻辑的过渡；Swiss 可能偏向网格秩序与几何裁切；Cinematic 可能偏向景深、镜头运动和戏剧化揭示。这些**都不是已经确认的最终主题规范**。

### 2.2 可应用的设计系统（Design System）〔核心〕

从此前讨论中归纳六个主要维度：

| 维度 | 主题可提供的内容 | 设计要点 |
|---|---|---|
| 色彩 | 语义色、背景、表面、文字、强调、辅助图表色、渐变 | 描述用途，而不是只存一组色值 |
| 字体 | 标题/正文/数字字体及回退、字重、行距、视觉层级 | 对中文、英文及离线设备做兼容处理 |
| 空间与排版 | 留白倾向、栅格、边距、对齐与密度气质 | 是布局语言，不是强制坐标 |
| 图形语言 | 线条、形状、边角、阴影、材质、背景与装饰 | 体现辨识度，避免只改颜色 |
| 元素风格 | 标题、正文、图片、图表、表格、卡片、连接线的默认表现 | 元素允许局部覆盖 |
| 动效语言 | 节奏、连续性、运动方式、空间感、强度 | 描述运动哲学，不强制定时轨迹 |

所有主题都应能产生合法、可渲染的默认视觉效果；不要求每套主题都塞满所有参数。可缺省项由 SP 基础系统补足。

### 2.3 可选设计资源（Design Assets）〔optional，已确定〕

- 可选布局：封面、图文、数据、时间轴、对比、过渡等，主题可以零附带。
- 可选组件：特殊卡片、信息图、图形和连接结构等。
- 视觉资源：图案、背景、装饰、插画、授权字体等。
- **标志性资源（Signature Assets）**：真正体现此设计语言个性的图形、视觉效果和专属动效。

数量不作为主题质量指标。极简主题可以很轻；表现力复杂的主题可以很丰富。

### 2.4 视觉参考（Visual References）〔both，已确定〕

主题参考系统支持同时容纳：

1. **静态参考图**：传达风格气质、构图、材料、排版特征；可来自经许可使用的网页、平面作品或幻灯片。
2. **可编辑 SP 页面案例**：示范设计元素如何组合；AI 可以读取结构，用户可以修改。
3. **动态参考**（推荐）：短动画、过渡效果、交互预览；不是每套主题必需。
4. **简短设计意图说明**（推荐）：解释案例为何属于这种语言，而非要求照抄。

`both` 指框架同时支持参考图与可编辑实例，不意味着每套主题必须强制配齐规定数量。

推荐参考集合具有多样性：封面、正文、数据/流程、过渡，既要有典型案例，也可以有允许大胆变化的边界案例。**参考是理解与灵感，不是固定模板**。

### 2.5 AI 设计上下文（AI Design Context）〔推荐为可选〕

主题可向 AI 提供简洁的身份描述、关键特点、示例索引和可用资源能力说明。避免大篇幅重复设计常识，避免写成固定的十步执行流程。

建议按需加载：主题摘要 → 设计资料 → 特定示例/动效资源。强模型仍需要高质量的视觉信息，但不需要无谓限制。

## 3. 布局：主题不垄断页面结构

### 3.1 三种布局来源〔推荐〕

| 来源 | 作用 | 是否受主题限制 |
|---|---|---|
| SP 通用布局库 | 快速建立常见内容骨架 | 所有主题均可使用 |
| 主题特色布局 | 表达特定语言中的经典构图 | 可选，不强制 |
| AI / 用户自由布局 | 针对特殊内容创造新的空间结构 | 不要求存在预设布局 ID |

**核心原则**：页面首先由可编辑元素组成，预设布局只是创作起点。AI 可以不选择任何预设，自主创造流程图、动态图解、空间结构等内容。

### 3.2 应用布局 vs 参考布局

- **应用布局**：实例化为常规可编辑元素，可继续拆分、移动、删改；推荐作为默认。
- **参考布局**：AI 阅读其视觉与结构特征，自由创作新构图。
- 与布局源保持联动的“母版式”能力可在将来独立设计，不提前要求所有布局持久绑定主题。

## 4. Motion Language 与主题标志性动效

### 4.1 动效不是固定播放表〔已确定〕

主题描述五个方面：

- **Rhythm**：节奏（轻快、舒缓、克制、戏剧性等）。
- **Movement**：运动倾向（平移、缩放、展开、裁切、形变等）。
- **Continuity**：元素是否强调连续关系与跨页身份。
- **Depth**：平面、层叠、景深或空间透视。
- **Intensity**：表现强度与视觉冲击。

具体对象、先后顺序、时间线和叙事由 AI 或用户根据内容决定。

### 4.2 通用能力 + 主题专属资源〔推荐〕

建议分层：

- **SP Core Motion**：基础进入/退出、碎片展示、跨页匹配、路径、遮罩、缓动、时间线能力。
- **Theme Signature Motion**：针对特定设计语言调校或原创的视觉效果（例如柔性形态衔接、几何裁切、镜头式推进）。
- **Cross-theme Adaptation**：将某种效果保留其核心能力，按另一主题的运动语言调整表现。

资源应当**可理解、可配置、可组合**。比如同一个形态变化能力，AI 能自由选择目标元素、路径、速度和关联对象，不只能“开启/关闭一个效果”。

### 4.3 资源跨主题使用时的两种选择

1. **原样使用**：保留资源原有的完整视觉气质，适合有意混搭。
2. **适配当前主题**：保留效果能力，但优先采用当前主主题的节奏、配色、材质和线条语言。

适配行为应是有界、可预览、可撤销的操作；不要把某主题的资源通过继承整个另一个主题来实现。

### 4.4 已有动画的处理

普通主题切换不删除专属动画，也不重写它们的完整编排；新创建动画可采用新主题的默认语言。可另外提供“适配当前主题”操作，供 AI 给出调整方案。

## 5. 主题切换：Skin 是默认行为〔已确定〕

### 5.1 Skin 与 Redesign 分离

| 操作 | 改动范围 | 是否默认 |
|---|---|---|
| **Skin：换肤** | 与主题关联的颜色、字体、组件默认效果、背景等 | **是** |
| **Adapt：风格适配** | 按需协调跨主题资源、动画气质和风格冲突 | 非默认，独立操作 |
| **Redesign：重新设计** | 允许 AI 改变布局、构图、叙事及动画编排 | 非默认，明确触发 |

Skin 应保留文本、图片、图表数据、页面顺序、元素结构、坐标、分组与已有动画关系。

### 5.2 样式归属：关联与覆盖〔推荐〕

每个元素的不同属性可以独立处于以下状态：

- **主题关联（Linked）**：例如 `text.primary`，主题切换时更新。
- **固定覆盖（Explicit Override）**：例如品牌 Logo 红色，主题切换时保留。
- **混合状态**：字体跟随主题、颜色固定、字号人工设定。

不以“修改来自 AI 还是人类”为区分：用户手动编辑与 AI 修改的优先级相同；真正重要的是属性来源与覆盖意图。

推荐的优先关系：**SP Base → 主题家族 → 主题变体 → 文稿覆盖 → 页面覆盖 → 元素覆盖**。

### 5.3 主题换肤的现实边界

即使不改变文本框坐标，新字体也可能改变换行、内容高度、图表标签尺寸。故 Skin 只承诺**不主动重排文档结构**，不承诺像素级完全不动。

应提供主题切换前后的可视预览、可撤销操作，以及文字溢出、字体缺失、可读性与对比度检测；**检测结果不等于强制自动修复**。用户可选择 AI 针对性修正。

## 6. 主题继承与资源复用

### 6.1 浅继承〔推荐〕

使用较浅层级：

`SP Base → Theme Family → Theme Variant`

例如 Noema 家族下可以包含 Light、Dark、Editorial 等变体；它们共享视觉身份，但覆盖颜色、字体或部分资源配置。避免多层主题相互继承造成来源不可追踪。

### 6.2 一个主主题 + 可组合资源〔推荐，非不可变约束〕

文稿默认选用一个主主题以维持视觉统一，但允许：

- 页面级或元素级个性化覆盖；
- 引入来自其他主题的**明示资源引用**；
- 采用独立的 Motion Library 与公共组件库；
- 用户明确要求时进行更大胆的跨主题混搭。

**继承**用于共享家族设计身份；**引用**用于跨家族复用资源，不能混为一谈。

### 6.3 共享资源与专属身份并存

资源来源建议区分：SP 通用库、主题专属库、跨主题适配资源。一个资源可以保留所属主题和原始气质，又能被其他主题调用。

概念上建议为资源保留：唯一标识、版本、依赖、可编辑性、离线 HTML 兼容性、预览和可调参数。具体数据 Schema 尚未冻结。

### 6.4 设计成果的复用粒度

当 AI 创造出优秀页面时，不必自动将其保存为新主题。可以根据目标选择：

- 保存**布局**：重用空间组织。
- 保存**组件**：重用某个图形/信息模块。
- 保存**动效**：重用某段时间线或转场能力。
- 保存**模板**：重用整份演示结构。
- 提炼**主题**：抽象出真正跨页面、跨项目稳定的设计语言。

以此防止主题库被仅有细微区别的页面挤满。

## 7. AI-Native：让强模型获得知识而不是束缚

### 7.1 技术硬约束与设计软指导

- **硬约束交给系统**：SP 文档结构合法、元素引用有效、导出文件完整、资源安全、可撤销与冲突检查。
- **设计软指导交给主题**：视觉理念、示例、材质、运动特征、优先使用的资源。
- **创作决策交给 AI 和用户**：内容规划、构图、组件创新、动画叙事、是否突破参考。

原则：**Constraints on validity, freedom in creativity.**

### 7.2 Skill 与主题的关系〔推荐〕

不要求每个主题都有独立 Skill。建议：

- 一份轻量的通用 SP Skill：介绍 MCP 能力、文档操作、预览与校验接口。
- 每个主题可有简明 AI Design Context，作为知识而非固定工作流。
- 复杂科学动画、数据叙事、主题创建等**跨主题创作方法**可以拥有可选专用 Skill。
- 内容按需读取，避免把上百套主题规范一次性塞进上下文。

### 7.3 推荐的 AI 主题读取层级

1. 主题搜索结果：名称、视觉身份、标签、缩略图。
2. 详细资料：语义样式、动效语言、专属能力、可用资源。
3. 按需参考：特定封面、内容页、动态图例、可编辑结构与设计意图。

通过 SP MCP 暴露读取和应用能力；MCP 负责执行编辑、渲染与结构检查，**不替模型规定具体创作方案**。没有必要立即锁定 MCP 工具名称或数量。

### 7.4 风格一致性不是“复刻每一页”

建议维护：

- **典型案例（Positive）**：鲜明表达核心身份。
- **边界案例（Boundary）**：体现该语言允许的创新和变化。
- **反例（Negative，可选）**：看似相近但失去风格特征的案例。

不同内容类型中（封面、数据、学术、流程、过渡）仍能识别出共同设计语言，比所有页面长得一样更能说明主题成功。

## 8. 借鉴 Claude Design 的设计语言提炼方法

此前讨论认为，值得借鉴的不是某种固定视觉风格，而是**从实际作品与视觉反馈中提取可复用设计语言**的过程。

推荐的六阶段概念流程：

1. **Collect：收集参考**——已有 PPT、网页、截图、动效片段、品牌或设计描述。
2. **Extract：提炼视觉基因**——找出稳定特征、偶然元素和参考之间的冲突。
3. **Explore：探索方向**——生成 2–3 个有明显区别的设计候选。
4. **Demonstrate：场景演示**——以相同内容验证封面、内容、数据/流程、动态过渡。
5. **Refine：人工反馈**——保留喜欢的部分，通过对话和画布共同调整。
6. **Publish：形成主题**——将身份、样式、动效语言、示例与可选专属资源归档。

未来可以存在 **Design Language Studio**（设计语言工作台），但它是产品方向设想，**尚未确认是否开发或何时开发**。

建议先以 Noema 进行小范围设计语言提炼实验，避免先制造一套庞大 Schema，再要求所有风格适配它。Noema 当前示例只是探索材料，不代表最终风格定义已经冻结。

## 9. 导出与长期可移植性

SP 已确定的总体文件目标是**默认导出可编辑、单文件、可离线放映的 HTML**。主题系统必须服从这一目标。

设计建议：

- 文稿保存所用主题的**必要样式快照与资源版本**，不能只存远程 `themeId`。
- 导出时只内嵌**实际使用的资源**和必要动画运行时，避免把整套主题生态打入文件。
- 主题下架、升级或 SP 网站不可达时，旧 HTML 仍应保持独立放映，并能依据嵌入项目数据恢复编辑。
- 字体内嵌须遵守授权；不支持内嵌时提供可靠回退与布局风险提示。
- 主题专属复杂效果要有兼容说明与必要的降级策略。
- 可编辑 HTML 可能携带隐藏页面、备注和原始设计资源，导出时应提示数据可见性。
- 第三方或社区主题默认不运行任意未受信任脚本。

---

## 10. 主题库规模与治理

此前出现过的目标：第一批约 **10–15 套高质量且彼此不同的主题**，逐步扩展到 **30–50、100+**，长期视实际需求扩展至数百套。这是**规划方向，不是冻结交付指标**。

主题数量不以配色变体凑数。应区分：

- **主题家族**：独立设计语言。
- **主题变体**：如 Light / Dark / Editorial。
- **设计资源**：单个布局、组件、动效或图形。
- **模板**：完整可编辑演示文稿。

未来主题来源可以是官方、个人和社区；社区方案、安装机制、审核、版权与脚本扩展权限均未定。

## 11. 以 Noema 为例的概念框架（非最终规范）

| 层次 | 可能的内容 | 状态 |
|---|---|---|
| 视觉身份 | 清晰层级、灵活留白、空间连续性 | 探索假设 |
| 基础参数 | 中性色调、对比明确的字体、克制装饰 | 探索假设 |
| 标志性资源 | 柔性位移、形态衔接、层级展开、细腻遮罩 | 创意候选 |
| 视觉参考 | 封面、内容、数据、过渡等静态图与可编辑实例 | 推荐方法 |
| AI 上下文 | 简洁的设计理念、案例索引、资源介绍 | 推荐形式 |

Noema Light / Dark / Editorial 可以共享家族身份、拥有不同样式变体；其专属动效也可被其他主题引用。需要避免把 Noema 简化成“米白背景 + 大标题 + 三张卡片”的固定模板。

## 12. 需继续讨论、尚未冻结的决策

| 问题 | 当前倾向 | 为什么尚未决定 |
|---|---|---|
| 主主题能否在单页切换成完整第二主题 | 默认一个主主题 + 局部覆盖 | 需要处理语义 Token 与动画冲突 |
| 如何对跨主题 Signature Motion 进行自动适配 | 原样使用 / 适配当前主题 两种选项 | 要验证美术一致性与可逆性 |

| 哪些 Theme Signature Effects 需要专有运行时 | 优先通用动画描述，特殊模块另审 | 离线 HTML 体积、安全、兼容性成本 |
| 视觉参考每套至少几个 | 以跨场景质量为主 | 不用硬性数量限制创造空间 |
| AI 主题指南是否作为文件独立交付 | 可选 Design Context + 通用 Skill | 避免每主题维护独立 Skill |
| Design Language Studio 如何设计 | 参考输入 → 多方向 → 实例验证 → 固化 | 仍处产品概念阶段 |
| 主题库对第三方扩展的开放程度 | 先声明式资源，再逐步扩展 | 需要独立讨论安全、许可、质量审核 |

### 建议的下一轮讨论焦点

**优先通过一套真实设计语言（可用 Noema）验证三个问题**：

1. 什么样的视觉差异足以称为不同主题家族，而不仅是变体？
2. 一个特色动效如何在同一主题内保持辨识度、跨主题时又能选择保留原貌或适配？
3. 对强模型而言，哪种参考组合（简短理念 / 视觉图片 / 可编辑案例 / 动效演示）最能改善作品而不限制创造力？

不需要此时进一步细化代码、数据库、接口表或者批量创作主题包。

## 14. 一句话总结

> **SP 的主题不是限制页面长相的模板，而是为人类和 AI 提供设计身份、视觉知识及专属表现资源的一门设计语言。** 它应当有明确个性，却允许自由布局、跨主题组合和原创动效；切换主题默认换肤不重构，最终作品仍可保存为独立、可编辑的 HTML。
